PersistNewAdsAsync		 SaveChangesAsync called once per new ad inside the card loop ✓ Fixed

For a page with 50 new ads that is 50 sequential Postgres round-trips. On a board with 10 pages and all-new ads, that is up to 500 individual writes per run instead of at most 10 (one per page).

ToListAsync fetches all active ads then filters in C#. For a board with thousands of accumulated ads this is an unbounded memory allocation and client-side evaluation.

8 AdScoringRepository
UpsertAsync		 Upsert implemented as delete-then-insert — not atomic

Between the DELETE and the INSERT there is a brief window where no row exists. A concurrent scoring job for the same ad could race on the insert and trigger a unique-constraint violation. PostgreSQL's native ON CONFLICT DO UPDATE eliminates this window entirely.

 Correctness Use a raw SQL INSERT … ON CONFLICT (job_ad_id) DO UPDATE SET … via ExecuteSqlRawAsync, or use EF Core 8's ExecuteUpdateAsync for the existing-row path. Low — Isolated to the repository class; no schema change needed.
9 AdScoringJob
ExecuteAsync ~L115 (finally)		 Cleanup save in finally uses the job's CancellationToken — bug

If the job is cancelled, ct is already in a cancelled state when the finally block runs. SaveChangesAsync(ct) and PublishAsync both throw OperationCanceledException, leaving the ad permanently stuck with IsScoringPending = true and never emitting the SSE event. ScrapeJobRunner correctly uses CancellationToken.None in its cleanup blocks.

 Bug Pass CancellationToken.None to both SaveChangesAsync and PublishAsync inside the finally block. Trivial — Two-argument changes; zero risk.
10 AdScoringJob ~L70
+ ClaudeAiProvider ~L151		 ISettingsRepository.GetAsync called twice per scoring job

The settings row (a single-row table) is fetched once in AdScoringJob.ExecuteAsync (to check for a resume) and again inside ClaudeAiProvider.ScoreAdAsync (to read the model name). Two round-trips to Postgres for identical data within the same logical operation.

 Performance Pass the already-loaded model name string as a parameter to IAiProvider.ScoreAdAsync, or cache settings in a short-lived IMemoryCache (e.g. 60 s TTL). Low — Small interface change to IAiProvider; all callers are in the same solution.
11 JobAdsController
ApplyPartialMatchFilter ~L543		 Case-insensitive search uses string.ToLower() — prevents index use

EF Core translates .ToLower().Contains(value) to LOWER(field) LIKE '%value%'. This forces a full-table scan on every filtered request and is incompatible with pg_trgm GIN indexes or Postgres's native ILIKE.

 Performance Replace with EF.Functions.ILike(field, $"%{value}%") which maps to ILIKE. Add CREATE INDEX … USING GIN (title gin_trgm_ops) if query latency on large datasets becomes a concern. Low — Code change is trivial; index creation is non-blocking in Postgres but requires a migration.
12 PlaywrightScraperEngine
(Singleton)
GetBrowserAsync		 No browser crash recovery

The singleton _browser field is set once. If the Chromium process crashes (OOM, segfault, container OOM-kill) mid-run, subsequent calls will attempt to use a disconnected browser and throw on every scrape until the application is restarted.

 Resilience In GetBrowserAsync, check _browser?.IsConnected == true before returning the cached instance. If disconnected, null out _browser and _playwright, re-acquire the SemaphoreSlim, and re-initialize. Medium — Concurrent callers during re-init need careful handling; the existing lock already provides the right structure.
13 Program.cs ~L44 Hangfire dashboard has no authentication

Authorization = Array.Empty<IDashboardAuthorizationFilter>() exposes full job history (including board URLs and parameters), manual job trigger/delete, and worker status to anyone who can reach the port. Acknowledged in a comment but unresolved.

 Security Use Hangfire's built-in LocalRequestsOnlyAuthorizationFilter for local dev, or add a simple header/env-var token filter. Must be hardened before any non-localhost deployment. Low — Additive change; does not affect functionality.
14 ScrapeJobRunner
JobBoardsController
(/refresh endpoint)		 No distributed lock prevents two concurrent scrape runs on the same board

A manual /refresh trigger while the scheduled run is already executing starts a second ScrapeJobRunner for the same JobBoardId: two Playwright pages consumed, two ScrapeRun records created, and a race on LastScrapedAt. The duplicate-key catch in ProcessAdCardAsync treats the symptom, not the cause.

 Code Quality Add [DisableConcurrentExecution(timeoutInSeconds: 0)] to ScrapeJobRunner.ExecuteAsync (Hangfire distributed lock keyed by jobBoardId), or check for an existing Running ScrapeRun for that board before creating a new one and return early. Low — DisableConcurrentExecution is a one-attribute fix with no logic change.

What is well-implemented

  • Clean layer separation — Core / Infrastructure / Jobs / Api boundaries respected throughout
  • Forced AI tool-use with retry-backoff, per-operation timeouts, and configurable models
  • Correct multi-column cursor pagination sort key (IsPinned DESC, ScrapedAt DESC, Id DESC)
  • Bulk mutations via ExecuteUpdateAsync — single SQL UPDATE per bulk action, no change-tracking overhead
  • Timestamp interceptor — clean, non-intrusive, correctly registered as Singleton
  • Stale run cleanup job — 30-minute orphan detection guards against hung Playwright sessions
  • JSONB for complex types — ScraperConfig, ScrapeRun.Errors, AdScoring.Requirements stored as JSONB rather than normalised tables
  • CSS selector determinism — no per-ad AI call; all field extraction is done via AI-generated selectors
  • Playwright browser-context isolation — new context per render, no cross-run cookie/session contamination
  • OperationCanceledException propagation — cancellation is correctly distinguished from other failures throughout the retry loops
