8 AdScoringRepository
UpsertAsync		 Upsert implemented as delete-then-insert — not atomic

Between the DELETE and the INSERT there is a brief window where no row exists. A concurrent scoring job for the same ad could race on the insert and trigger a unique-constraint violation. PostgreSQL's native ON CONFLICT DO UPDATE eliminates this window entirely.

 Correctness Use a raw SQL INSERT … ON CONFLICT (job_ad_id) DO UPDATE SET … via ExecuteSqlRawAsync, or use EF Core 8's ExecuteUpdateAsync for the existing-row path. Low — Isolated to the repository class; no schema change needed.

10 AdScoringJob ~L70

The settings row (a single-row table) is fetched once in AdScoringJob.ExecuteAsync (to check for a resume) and again inside ClaudeAiProvider.ScoreAdAsync (to read the model name). Two round-trips to Postgres for identical data within the same logical operation.

11 JobAdsController
ApplyPartialMatchFilter ~L543		 Case-insensitive search uses string.ToLower() — prevents index use

EF Core translates .ToLower().Contains(value) to LOWER(field) LIKE '%value%'. This forces a full-table scan on every filtered request and is incompatible with pg_trgm GIN indexes or Postgres's native ILIKE.

 Performance Replace with EF.Functions.ILike(field, $"%{value}%") which maps to ILIKE. Add CREATE INDEX … USING GIN (title gin_trgm_ops) if query latency on large datasets becomes a concern. Low — Code change is trivial; index creation is non-blocking in Postgres but requires a migration.

What is well-implemented

  • Clean layer separation — Core / Infrastructure / Jobs / Api boundaries respected throughout
  • Forced AI tool-use with retry-backoff, per-operation timeouts, and configurable models
  • Correct multi-column cursor pagination sort key (IsPinned DESC, ScrapedAt DESC, Id DESC)
  • Bulk mutations via ExecuteUpdateAsync — single SQL UPDATE per bulk action, no change-tracking overhead
  • Timestamp interceptor — clean, non-intrusive, correctly registered as Singleton
  • Stale run cleanup job — 30-minute orphan detection guards against hung Playwright sessions
  • JSONB for complex types — ScraperConfig, ScrapeRun.Errors, AdScoring.Requirements stored as JSONB rather than normalised tables
  • CSS selector determinism — no per-ad AI call; all field extraction is done via AI-generated selectors
  • Playwright browser-context isolation — new context per render, no cross-run cookie/session contamination
  • OperationCanceledException propagation — cancellation is correctly distinguished from other failures throughout the retry loops

F1 app/**/*.tsx
(all 9 page files) 		Every page is a Client Component — zero Server Components used✓ Fixed

Every app/ page starts with 'use client', which forces the full React runtime and all hook dependencies to be downloaded, hydrated, and executed on first load, even for pages whose initial render has no interactivity. Next.js 14 App Router defaults to Server Components precisely to avoid this.

 Performance Keep pages as Server Components (no 'use client') and split the interactive parts into small leaf Client Components. For example, app/ads/page.tsx could be a Server Component that renders the page shell and imports a AdsClient.tsx Client Component that owns all hooks and filter state. This enables partial pre-rendering and reduces the JS sent on first load. Medium — Requires reorganising page files; hooks cannot live in Server Components, so interactive sub-trees must be carefully isolated.
F2 app/ads/page.tsx
app/applications/page.tsx
components/ads/AdTable.tsx 		No virtual scrolling — DOM grows unbounded as user pages through infinite lists✓ Fixed

useInfiniteQuery appends pages to an in-memory array; every fetched item is rendered as a DOM node. Loading 5 pages × 50 ads = 250 table rows, all painted and kept alive. Scrolling performance degrades significantly beyond ~300 items, and memory usage climbs with every "Load more" click.

 Performance Integrate @tanstack/react-virtual (already compatible with TanStack Query and the existing infinite query setup). The virtualiser renders only the ~10–20 rows visible in the viewport at any time. The "Load more" trigger can be replaced with an intersection observer on a sentinel element at the bottom of the virtual list, enabling seamless infinite scroll. Medium — Requires refactoring table rendering; row height consistency must be ensured for accurate virtualisation.
F3 components/ads/FilterBar.tsx
components/ads/AdTable.tsx 		Missing React.memo, useMemo, and useCallback in render-heavy components✓ Fixed

Several expensive computations and callback recreations happen on every render: FilterBar.tsx recreates update, toggle, and getBoardName inline on every parent re-render; AdTable.tsx runs ads.every(a => selectedIds.has(a.id)) — O(n) — on every render; chip lists and suggestion arrays are rebuilt on every keystroke. The BulkActionMenu sub-component is not memoised despite being stable across most renders.

 Performance Wrap stable child components with React.memo (BulkActionMenu, Chip, AdScoringPanel). Wrap inline functions with useCallback and computed arrays/values with useMemo. The allSelected derived flag should be useMemo(() => ads.every(...), [ads, selectedIds]). Low — Additive-only changes; incorrect dependency arrays are the main pitfall to watch for.
F4 components/ui/RichTextEditor.tsx
web/package.json (8 Tiptap pkgs) 		Tiptap + ProseMirror (~200 KB gzipped) loaded on every page, not code-split✓ Fixed

RichTextEditor is used only on the /applications/[id] page, inside the Job Ad tab, only when the user clicks "Edit". Nevertheless, all 8 Tiptap packages (StarterKit, Color, TextStyle, FontFamily, Highlight, Underline, ProseMirror core) are bundled into the main JS chunk delivered to every page on first load.

 Performance Replace the static import with next/dynamic: const RichTextEditor = dynamic(() => import('@/components/ui/RichTextEditor'), { ssr: false }). This defers the entire Tiptap bundle to a separate chunk that is only fetched when the application detail page is visited, with zero cost to all other routes. Additionally, audit which Tiptap extensions are truly needed — FontFamily and multi-colour Highlight have niche use cases and could be removed. Trivial — One import change; ssr: false is already correct (Tiptap is SSR-incompatible by default).

FilterBar.tsx hosts seven distinct sub-components (TypeaheadPicker, ScorePicker, Chip, CheckRow, TriStateCheckRow, BackButton, and the main FilterBar) in a single 766-line file. F6 lib/hooks/useFilterState.ts
app/ads/page.tsx
app/applications/page.tsx 		Filter state stored in localStorage — filters are not shareable or bookmarkable

Active filters are persisted to four localStorage keys (workcast:ads-filters, etc.). This means a filtered view cannot be copied as a URL, cannot be shared with another user or browser session, and is silently lost when the user opens a new tab. There is also a brief hydration flash on load where filters appear empty (default state) before useEffect reads localStorage.

 Architecture Migrate filter state to URL search parameters using Next.js's useSearchParams / useRouter. Each filter value becomes a ?titles[]=…&excludeLocations[]=… param. This makes filtered views instantly shareable, integrates with the browser back-button, eliminates the hydration flash, and removes the need for useFilterState entirely. The TanStack Query key already derives from filter values, so cache behaviour is unchanged. Medium — URL encoding of array filters requires a serialisation helper; all filter-reading code must switch from object state to useSearchParams.
F7 app/ads/page.tsx
app/applications/page.tsx 		Tab toggle + filter bar + total-count pattern duplicated across two pages

Both the Ads page and the Applications page implement the same structure: two useFilterState calls (main + trash), a view toggle between main and trash, an active/inactive query with enabled, a total-count query gated on hasActiveFilters, the same tab toggle JSX, and the same "Displaying X of Y" text. The two files are structurally ~80% identical.

Each page passes its query functions, filter storage keys, and render slots as props or children. The board-selector and status-flag derivation specific to the Ads page remain in ads/page.tsx. Low — Extraction only; no logic changes. The differences between the two pages are small enough to be handled by optional props.
F8 app/**/*.tsx
(no error.tsx files exist) 		No React Error Boundary — an uncaught render error kills the entire app✓ Fixed

There are no error.tsx files in any route segment and no ErrorBoundary component anywhere in the tree. If any component throws during render (e.g., a malformed API response, a null-dereference, or a Tiptap internal error), React unmounts the entire tree and shows a blank page with no recovery path for the user.

 Resilience Add an app/error.tsx file (Next.js 14 App Router's built-in error boundary mechanism). This automatically catches render errors in any child route, shows a friendly error UI, and provides a "Try again" button that calls reset() to attempt re-rendering. Add a second app/global-error.tsx for errors in the root layout itself. Trivial — Purely additive; does not affect any existing code path.
F9 lib/hooks/useSSE.ts
(lines 7–16, 37–97) 		SSE events use a flat interface with optional fields — type-unsafe dispatch with ! assertions✓ Fixed

The SseEvent interface declares all payload fields as optional (boardId?: string, runId?: string, adId?: string, applicationId?: string, unreadCount?: number). Each event handler then accesses these with non-null assertions (event.boardId!, event.applicationId!) without runtime validation. Adding a new event type or mistyping a field silently passes TypeScript but throws at runtime.

 Type Safety Replace the flat interface with a TypeScript discriminated union keyed on type:
type SseEvent = | { type: 'boardStatusChanged'; boardId: string; status: string } | { type: 'runStarted'; boardId: string; runId: string } | …
TypeScript then narrows the payload automatically inside each case branch, making the ! assertions unnecessary and making future events self-documenting.		 Low — Internal to one file; the discriminated union is a drop-in type replacement with no runtime change.
F10 lib/api.ts
types/index.ts 		No runtime API response validation — backend type changes cause silent failures

All API responses are cast with JSON.parse(text) as T (line 37 of api.ts). TypeScript types in types/index.ts are hand-maintained mirrors of the backend DTOs. If the backend renames a field, adds a required property, or changes a type, the frontend continues to compile and only fails at runtime — often with a confusing undefined value deep in a component rather than a clear error at the API call site.

 Type Safety Introduce Zod schemas for each response type. Define them in lib/schemas.ts and use schema.parse(JSON.parse(text)) in apiFetch. Zod's .parse() throws with a precise field-level error message immediately at the API boundary, surfaces mismatches during development, and infers the TypeScript type automatically — eliminating the hand-maintained types/index.ts interfaces. Alternatively, generate types from the backend's OpenAPI schema (Swashbuckle already configured) using openapi-typescript. Medium — Zod adds a runtime dependency; schema definitions must be maintained in sync with the backend. Starting with one or two critical types (Application, JobAd) rather than all at once reduces risk.

What is well-implemented (Frontend)

  • TanStack Query as the sole source of truth for server state — no Redux, no duplication
  • SSE + polling hybrid strategy — SSE events for instant updates, 3–60 s interval as a fallback safety net
  • Correct cursor-based infinite scroll with useInfiniteQuery and getNextPageParam
  • useSSE mounted once at the app root via SSEProvider — no duplicate connections per component
  • Predicate-based selective query invalidation — avoids over-invalidating unrelated queries on SSE events
  • setQueryData for the unreadCountChanged SSE event — instant badge update with no network round-trip
  • Filter state handles schema evolution gracefully — spread-merge with EMPTY_FILTERS absorbs new fields without data loss
  • ScoringShared.tsx — good extraction of CATEGORY_STYLES, ScoringSpinner, ScoringErrorBanner, and ScoringRequirementsGrid
  • FilterBar features opt-in system — features prop array keeps the component flexible without prop proliferation
  • Consistent API wrapper pattern in lib/api.ts — all calls go through a single typed apiFetch with unified error parsing
  • Tri-state filter support (include / exclude / none) implemented cleanly as a state machine in FilterBar
  • Total-count queries gated behind enabled: hasActiveFilters() — no wasted request when no filters are active
  • Dynamic refetchInterval that drops to 3 s during scoring and rises back to 60 s when idle
