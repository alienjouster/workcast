# CONVENTIONS.md — Workcast Platform
# Coding Conventions & Standards

All agents must follow these conventions consistently. Consistency across
agents is more important than personal preference. When in doubt, follow
what is already established in the codebase.

---

## .NET Conventions

### Naming
- Classes, interfaces, enums: PascalCase
- Methods, properties: PascalCase
- Private fields: _camelCase (underscore prefix)
- Local variables, parameters: camelCase
- Constants: UPPER_SNAKE_CASE
- Interfaces: prefix with `I` (e.g. `IAiProvider`)
- Async methods: suffix with `Async` (e.g. `ExtractJobAdAsync`)

### File Organisation
- One class/interface/enum per file
- File name matches type name exactly (e.g. `JobBoard.cs` contains `class JobBoard`)
- Namespace matches folder path: `Workcast.Core.Entities`, `Workcast.Infrastructure.AI`, etc.

### Null Handling
- Enable nullable reference types in all projects: `<Nullable>enable</Nullable>`
- Use `?` for nullable types, never suppress with `!` without a comment explaining why
- Prefer null-coalescing (`??`) and null-conditional (`?.`) over explicit null checks where readable

### Error Handling
- Never swallow exceptions silently — always log before re-throwing or handling
- Use `OperationCanceledException` propagation — do not catch and ignore cancellation
- Domain-level failures (e.g. board analysis failed) should set entity status rather than throw to the caller
- Infrastructure failures (network, DB) should throw and be caught by the Hangfire retry mechanism

### Async
- Always use `async`/`await` — no `.Result` or `.Wait()` anywhere
- Always pass `CancellationToken` through the full call chain
- Use `ConfigureAwait(false)` in library/infrastructure code

### Dependency Injection
- Register all services in `DependencyInjection.cs` extension methods per project
- Lifetimes:
  - `AppDbContext` → Scoped
  - `PlaywrightScraperEngine` → Singleton (browser instance is expensive)
  - `ClaudeAiProvider` → Scoped
  - `AiExtractionService` → Scoped
  - `HangfireJobScheduler` → Singleton
  - `HtmlCleaningService` → Singleton (stateless)

### Configuration
- All config bound via `IConfiguration` using strongly-typed options classes
- Options classes live in the project that uses them
- Never read `IConfiguration` directly in business logic — inject the options class

```csharp
// Example options class
public class AnthropicOptions
{
    public const string SectionName = "Anthropic";
    public string ApiKey { get; init; } = string.Empty;
    public string Model { get; init; } = "claude-sonnet-4-5";
}

// Registration in DependencyInjection.cs
services.Configure<AnthropicOptions>(config.GetSection(AnthropicOptions.SectionName));
```

### Entity Design
- Entities use private setters with public factory methods or constructors
- No parameterless constructors on entities (EF Core uses the private one)
- IDs are `Guid`, generated by the database default (`gen_random_uuid()`)
- `CreatedAt` and `UpdatedAt` set via EF Core interceptor, not manually

```csharp
// Entity pattern
public class JobBoard
{
    private JobBoard() { } // EF Core constructor

    public static JobBoard Create(string url, string? name = null)
    {
        return new JobBoard
        {
            Url = url,
            Name = name,
            Status = BoardStatus.Pending,
            ScheduleCron = "0 * * * *",
        };
    }

    public Guid Id { get; private set; }
    public string Url { get; private set; } = string.Empty;
    // ...

    public void Activate(ScraperConfig config)
    {
        ScraperConfig = config;
        Status = BoardStatus.Active;
    }
}
```

## Database Conventions

- Table names: snake_case plural (e.g. `job_boards`, `job_ads`, `scrape_runs`)
- Column names: snake_case (e.g. `created_at`, `scraper_config`)
- Foreign keys: `{referenced_table_singular}_id` (e.g. `job_board_id`)
- All timestamps: `TIMESTAMPTZ` (timezone-aware)
- UUIDs: `uuid` type with `DEFAULT gen_random_uuid()`
- JSONB columns for: `scraper_config`, `errors`
- Indexes defined in `IEntityTypeConfiguration` classes, not in migrations directly

## REST API Conventions

### DTOs
- Request DTOs: suffix `Request` (e.g. `CreateJobBoardRequest`)
- Response DTOs: suffix `Response` (e.g. `JobBoardResponse`)
- DTOs are records with `init` setters
- Never expose entities directly from controllers — always map to DTOs

## Frontend Conventions (Next.js)

### Naming
- Components: PascalCase files and function names (e.g. `BoardCard.tsx`)
- Hooks: camelCase with `use` prefix (e.g. `useJobBoards.ts`)
- API functions: camelCase (e.g. `fetchJobBoards`, `createJobBoard`)
- Types/interfaces: PascalCase (e.g. `JobBoard`, `ScrapeRun`)

### File Organisation
- One component per file
- Co-locate component-specific types in the same file unless shared
- Shared types in `types/index.ts`
- All API calls in `lib/api.ts` — no fetch calls in components or hooks

### Component Pattern
- Prefer Server Components for data display pages
- Use Client Components (`'use client'`) only when interactivity or hooks are needed
- Keep Client Components as leaf nodes — pass data down from Server Components where possible

### API Client Pattern
```typescript
// lib/api.ts — all functions follow this pattern
const API_BASE = process.env.NEXT_PUBLIC_API_URL ?? 'http://localhost:8080';

async function apiFetch<T>(path: string, options?: RequestInit): Promise<T> {
  const res = await fetch(`${API_BASE}${path}`, {
    headers: { 'Content-Type': 'application/json' },
    ...options,
  });
  if (!res.ok) {
    const error = await res.json();
    throw new Error(error.detail ?? `API error ${res.status}`);
  }
  return res.json() as Promise<T>;
}

export const api = {
  boards: {
    list: () => apiFetch<JobBoardResponse[]>('/api/job-boards'),
    get: (id: string) => apiFetch<JobBoardResponse>(`/api/job-boards/${id}`),
    create: (data: CreateJobBoardRequest) =>
      apiFetch<JobBoardResponse>('/api/job-boards', { method: 'POST', body: JSON.stringify(data) }),
    // ...
  },
};
```

### TanStack Query Pattern
```typescript
// lib/hooks/useJobBoards.ts
export function useJobBoards() {
  return useQuery({
    queryKey: ['job-boards'],
    queryFn: () => api.boards.list(),
  });
}

// Polling example for pending boards
export function useJobBoard(id: string) {
  return useQuery({
    queryKey: ['job-boards', id],
    queryFn: () => api.boards.get(id),
    refetchInterval: (query) =>
      query.state.data?.status === 'pending' ? 3000 : false,
  });
}
```

### Styling
- Tailwind CSS utility classes only — no custom CSS files except `globals.css`
- No inline styles
- Responsive design: mobile-first with `sm:`, `md:`, `lg:` breakpoints
- Keep class lists readable — extract to a variable if over 5 classes

## Git Conventions

- Branch per agent: `agent/1-core`, `agent/2-infrastructure`, etc.
- Commit message format: `[Agent N] short description`
  - e.g. `[Agent 1] Add JobBoard entity and IAiProvider interface`
- One commit per logical unit of work — not one giant commit per agent
- No merge commits — use rebase

## What to Do When Uncertain

1. Re-read the relevant section of TECHSPEC.md
2. Re-read AGENTS.md for your boundary constraints
3. Follow the pattern already established in the codebase
4. If genuinely ambiguous, implement the simplest correct interpretation and add
   a comment: `// NOTE: [describe the ambiguity and your decision]`
5. Do not ask the user — make a reasonable decision and document it
